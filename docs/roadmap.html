📋 task-triage — разметить очередь по исполнителю (Cursor / чат)
# Промт: разметка задач по исполнителю (Cursor vs ты) — экономия токенов

Вставь в чат проекта (одного сайта). Самодостаточный. Задача: пройтись по дорожной
карте / очереди задач этого проекта и у каждой открытой задачи проставить режим
исполнения — кто её делает дешевле для владельца по токенам: Cursor (отдельная
подписка владельца) или ты (этот чат). Цель — чтобы владелец не жёг токены там,
где работу дешевле отдать Cursor, и не терял качество там, где отдавать нельзя.

Это разметка плана, а не выполнение задач. Ничего из очереди сейчас не делаешь —
только оцениваешь и проставляешь теги. Деплой/код не трогаешь.

## Логика деления (с обоснованием — держи его при оценке)

Токены владельца жрёт в основном чтение контекста + написание кода в этом чате.
Cursor работает на своей подписке → вынеся туда «тяжёлое писательство», владелец снимает
его со своего бюджета. Но проверка тоже стоит токенов: честно проверить = прочитать
дифф и часть того же контекста. Поэтому выгода = (сэкономил на написании) − (потратил
на промт + ревью + цикл правок).

Три режима:
- →cursor — механика / большой объём однотипного письма, конвенции простые и
  стабильные. Ты пишешь Cursor промт, он делает, ты — спот-чек (выборочно + сборка/
  линт), не полное ревью. Примеры: тираж готового паттерна на N файлов, boilerplate.
- →сам — делаешь в этом чате. Когда трудное — решить что делать, а не напечатать:
  судейские решения, контент (текст — это и есть продукт), или завязка на
  нестандартный стек/конвенции проекта, где Cursor промахнётся. Промт = почти вся работа.
- →гибрид — решение и каркас за тобой, тиражирование по образцу — Cursor.

Глубина проверки под режим: →cursor — спот-чек; →сам и всё рискованное — полное ревью.

## Критично: перед пометкой →cursor — проверь текущее состояние

Задача в плане может быть уже частично/полностью сделана — план отстаёт от кода.
Бегло сверься с репозиторием, прежде чем помечать. Пометить вслепую = отправить Cursor
дублировать или ломать уже готовое → чистый минус.
И наоборот: очень мелкая механика (1 файл) — экономии почти нет. Выигрыш — на объёме.

## Что сделать

1. Найди файл плана/очереди проекта (docs/WEEK-PLAN.md, TODO.md, *-backlog.md…), адаптируйся.
   Если внятного списка задач нет — не выдумывай, сообщи и остановись.
2. Добавь в начало очереди короткую легенду трёх режимов + правило глубины проверки.
   Токены пиши ровно →cursor / →сам / →гибрид — единообразно во всех проектах сети.
3. У каждой открытой задачи проставь тег с короткой причиной. Уже размеченные не дублируй.
4. Где помечаешь →cursor — сначала сверься с кодом; если задача устарела, поправь формулировку.
5. Есть визуальная витрина (roadmap.html / артефакт) — продублируй бейджи там и переопубликуй.
6. Правки плана и витрины закоммить одним коммитом. Код не трогай.

📋 crawl-errors — аудит и починка 404 / ошибок обхода
# Промт: аудит и починка 404 / ошибок обхода (по своему сайту)

Вставь в чат проекта (одного сайта). Самодостаточный. Задача: чтобы запросы людей и
краулеров не улетали в 404, а структурные «пустые» URL (корни листингов, пагинация,
старые адреса после миграции) отдавали нормальную страницу или честный 301.

## Данные (откуда брать свои 404)
- Cloudflare — коды ответа по реальному трафику (у проекта может быть `npm run traffic`;
  иначе срез сети в izn.project.stats/context/<домен>.md и cf_stats.py).
- Google Search Console — отчёт «Индексирование → Страницы» (404, Soft 404) + топ URL с показами.
- Свой sitemap и роутинг — что сайт обещает/линкует, но не отдаёт.

Главное — отделить настоящие 404 от шума ботов (/wp-login.php, .env — НЕ чиним). Чиним то,
что бьют реальные люди/краулеры, имеет внешние ссылки/спрос, или структурно должно быть.

## Частые структурные 404
- Корни листингов, которые 404-ят, пока дочерние живы (напр. /{locale}/tag/ при живых
  /{locale}/tag/<тег>/ — реальная находка, 1 011 запросов/нед на /ru/tag/).
- Пагинация, старые URL после миграции, варианты слеша/регистра, битые ссылки в sitemap.

## Как чинить (по ценности URL)
1. Реальная страница, если URL структурно нужен и несёт SEO-ценность (корень листинга →
   индекс-хаб со ссылками на дочерние). По образцу существующего роута, с порогом тонкого контента.
2. 301 на ближайшую релевантную страницу (в конфиге хостинга — .htaccess/_redirects/headers).
3. 410 Gone — если контент удалён навсегда.
Не оставлять soft-404, не плодить пустышки, не ломать существующие редиректы.

## Рамки
Не менять живые слаги; обе локали симметрично; проверить сборкой/экспортом.

## В ответе
Какие 404 нашёл (с числом запросов/показов), что по каждому сделал (страница/301/410/бот-шум),
какие файлы изменил, результат сборки, что отложил.

# Промт: делегирование написания контента Cursor (через бриф) — безопасно для YMYL

Вставь в чат проекта. Задача: масштабировать наполнение рубрик, отдавая Cursor черновик
прозы, но оставляя за чатом судейскую часть (структура + проверенные источники) и проверку.
Для YMYL-сайтов (здоровье/финансы/право), где плохой AI-контент роняет весь домен.

## Почему нельзя просто «Cursor, напиши статью про X»
- YMYL под строгими E-E-A-T фильтрами; на молодом домене пачка посредственных AI-статей
  тянет вниз весь сайт. Галлюцинации источников/цифр недопустимы.
- Контент идёт по схеме бриф → черновик → проверка.

## Что отдавать (по риску)
- Высокий риск (медлонгриды, финсоветы) → чат пишет сам или Cursor-драфт + полное ревью (→сам).
- Средний/низкий, есть шаблон (карточки, рецепты, структурные гайды) → годится для брифа (→гибрид).

## Роли
- Чат (НЕ отдаётся): тема по спросу, структура H2/H3, тезис каждого раздела, проверенные
  источники с URL, FAQ, frontmatter, внутренние ссылки на существующие материалы.
- Cursor: развернуть бриф в прозу по конвенциям проекта.
- Чат (проверка): источники не выдуманы и тезисам соответствуют, нет overreach, сборка проходит.

## Бриф (собирает чат)
Тема/слаг под спрос · эталон-файл того же типа · frontmatter + спец-поля · H2 с тезисами (не
прозой) · таблицы/компоненты · FAQ · 3–6 реальных источников с URL (собираешь сам, при нужде
веб-поиск) · 2–3 внутренние ссылки на живые страницы.

## Правила для Cursor
- Разворачивай ТОЛЬКО бриф; цитируй ТОЛЬКО источники из брифа; ничего не выдумывай.
- Чего в брифе нет — не додумывай, пометь [нужен источник].
- Следуй AGENTS.md / контент-конвенциям; обе локали RU+EN; добавь запись в конфиг, если нужно.
- Сборка проходит; ReadAlso/related — только на существующие страницы.

## Проверка после Cursor (перед публикацией)
Источники реальны и подтверждают тезисы · нет мед/фин overreach · цифры/дозы совпадают ·
frontmatter валиден, слаг не менялся, пара RU/EN на месте · сборка/линт зелёные.

Итог: чат тратит токены на бриф + проверку, Cursor — на объём прозы. На медлонгридах экономия
мала (бриф ≈ 60–70% работы), реальный выигрыш — на шаблонных типах (карточки, рецепты).
