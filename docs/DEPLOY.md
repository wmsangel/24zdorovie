# Публикация сайта

Проект собирается в статику (`output: "export"`) и живёт на shared-хостинге
с Apache за Cloudflare. Никакого Node на сервере нет: всё серверное поведение —
редиректы, заголовки, выбор локали — описано в `public/.htaccess`.

Боевой домен — **24zdorovie.com**. Каталог на хостинге — `public_html`.

## 1. Сборка

```bash
npm run build
```

Команда делает два шага: `scripts/gen-og.mjs` рисует OG-картинки, затем
Next собирает статику в `out/`.

Генератор картинок сверяет свой список рубрик с `src/config/categories.ts`
и **роняет сборку**, если рубрика объявлена в конфиге, но забыта в скрипте.
Так и должно быть: список в `.mjs` продублирован вручную (импортировать TS
оттуда нельзя), и без проверки забытая рубрика молча даёт 404 на `og:image`
у всех своих статей. Увидели такую ошибку — допишите рубрику в `CATEGORIES`
внутри `scripts/gen-og.mjs`, повторите сборку.

На выходе `out/` — около 200 МБ и ~8600 файлов, из них основное это
`ru/`, `en/` и `covers/`.

## 2. Заливка

```bash
npm run deploy
```

Одна команда: собирает сайт, сравнивает `out/` с тем, что уже лежит
на сервере, и отправляет **только разницу**. Публикация статьи — это обычно
пара мегабайт вместо 240, FTP-клиент не нужен вовсе.

Что происходит под капотом (`scripts/deploy.mjs`):

1. хеши всех файлов `out/` сверяются с `.deploy-state.json` — слепком
   прошлого деплоя (файл локальный, в `.gitignore`);
2. изменившееся пакуется в `tar.gz` частями примерно по 40 МБ;
3. каждая часть уходит через cPanel UAPI `Fileman::upload_files`
   и распаковывается на месте через API 2 `Fileman::fileop` (`op=extract`);
4. архив с сервера удаляется сразу, даже если распаковка не удалась;
5. файлы, исчезнувшие из сборки, удаляются (`op=unlink`).

Две вещи в этой цепочке неочевидны и обе выяснены на живом хостинге.
`destfiles` для `extract` обязан быть **абсолютным** путём: с относительным
cPanel считает его от каталога архива и создаёт внутри сайта вложенный
`public_html/`, а без `destfiles` вовсе распаковывает в домашний каталог,
где нет прав на запись. И `fileop` возвращает `result=1` даже когда
распаковщик отказал — настоящая причина приходит текстом в `output`,
поэтому скрипт разбирает его отдельно.

`tar.gz`, а не `zip`: в путях есть кириллица (страницы тегов), tar хранит
имена байтами и не зависит от кодировочных таблиц.

### Настройка (один раз)

```bash
cp scripts/.deploy.env.example scripts/.deploy.env
```

В файле нужны четыре вещи: хост cPanel, пользователь, API-токен и каталог.
Токен создаётся в cPanel → **Security → Manage API Tokens**.

> **`CPANEL_HOST` — не домен сайта.** `24zdorovie.com` проксируется Cloudflare,
> порт 2083 через него не пройдёт. Нужен прямой адрес сервера из панели GoDaddy
> (обычно вида `xxxxx.prod.iad2.secureserver.net`) или IP.

### Флаги

```bash
npm run deploy:dry              # план: что уедет и что удалится, без отправки
npm run deploy -- --selftest    # проверить связку на одном файле (robots.txt)
npm run deploy -- --no-build    # залить уже собранное out/
npm run deploy -- --full        # забыть состояние и залить всё заново
npm run deploy -- --no-delete   # ничего не удалять на сервере
npm run deploy -- --no-purge    # не трогать кэш Cloudflare
```

`--selftest` стоит гонять после любой смены хостинга или доступов: он
заливает один файл, распаковывает его и сверяет размер и время с локальным.
Это не формальность — cPanel отвечает «успех» и в тех случаях, когда
распаковщик на самом деле ничего не записал.

Первый запуск состояния не знает и зальёт все ~220 МБ семью частями — это
нормально и делается один раз. Дальше в работе остаются мегабайты.

Файлы от прежних заливок скрипт при первом запуске не трогает: он знает
только то, что отправил сам. Если на сервере остались страницы, которых
в сборке уже нет, их надо один раз удалить через File Manager — дальше
за этим следит сам скрипт.

Если к удалению вдруг оказывается больше 300 файлов, скрипт останавливается
и ничего не удаляет: столько обычно означает потерянный `.deploy-state.json`,
а не реально удалённые статьи. Посмотрите список через `npm run deploy:dry`
и, если всё верно, повторите с `--force-delete`.

> **`.htaccess` едет сам.** Он лежит в `out/.htaccess`, скрипт включает его
> в архив наравне с остальным и пишет об этом в лог. Это как раз то, что
> регулярно терялось при заливке FTP-клиентом: без него нет ни `/` → `/ru/`,
> ни HTTPS, ни заголовков кэша.

### Запасной путь, если API недоступен

```bash
cd out && tar -czf ../site.tar.gz . && cd ..
# залить site.tar.gz через File Manager в cPanel и распаковать на месте
```

## 3. Сброс кэша Cloudflare

Делается сам в конце `npm run deploy`, если в `scripts/.deploy.env` заданы
`CF_ZONE_ID` и `CF_API_TOKEN` (токен создаётся с правом **Zone → Cache Purge**
для этой зоны). Без токена шаг пропускается с напоминанием, деплой при этом
неудачным не считается; отключить его насовсем — `--no-purge`.

Зачем это нужно: в `.htaccess` для картинок, шрифтов, JS и CSS выставлен
`max-age=31536000, immutable`. Имена OG-картинок между сборками не меняются
(`nutrition-ru.png` и т.д.), поэтому при изменении их содержимого Cloudflare
без очистки отдавал бы старую версию целый год.

Руками — там же, в панели: **Caching → Configuration → Purge Everything**.
Точечно (до 30 адресов) — **Custom Purge**; для этого проекта хватает
`/og/*.png`, `/favicon.ico` и `/icon.svg`, потому что имена JS и CSS
от Next.js содержат хеш и меняются сами. HTML чистить не нужно вообще:
он отдаётся с `Cache-Control: private` и в кэш Cloudflare не попадает.

Соцсети и мессенджеры кэшируют превью у себя отдельно. Для уже расшаренных
ссылок карточка обновится не сразу; ускорить можно отладчиком Facebook или
ботом `@WebpageBot` в Telegram.

## 4. Проверка после заливки

```bash
# редиректы и заголовки — то есть доехал ли .htaccess
curl -sI https://24zdorovie.com/            | head -4   # ждём 302 → /ru/
curl -sI http://24zdorovie.com/             | head -3   # ждём 301 → https
curl -sI https://www.24zdorovie.com/        | head -3   # ждём 301 без www

# выбор локали на корне: кука важнее языка браузера, а язык браузера — важнее умолчания
curl -sI -H 'Accept-Language: ru-RU,ru;q=0.9' https://24zdorovie.com/ | grep -i location   # → /ru/
curl -sI -H 'Accept-Language: en-US,en;q=0.9,ru;q=0.8' https://24zdorovie.com/ | grep -i location  # → /en/
curl -sI -H 'Accept-Language: en-US,en;q=0.9' -H 'Cookie: locale=ru' https://24zdorovie.com/ | grep -i location  # → /ru/
curl -sI https://24zdorovie.com/ | grep -iE 'vary|cache-control'   # → Vary: Cookie…, Cache-Control: private

# страницы отвечают
for u in /ru/ /en/ /sitemap.xml /robots.txt /rss/ru.xml; do
  printf "%s %s\n" "$(curl -s -o /dev/null -w '%{http_code}' https://24zdorovie.com$u)" "$u"
done

# ни одна og:image не ведёт в 404
grep -rhoE 'og:image" content="https://24zdorovie\.com(/og/[a-z-]+\.png)"' out --include=index.html \
  | sed -E 's|.*com||;s|"$||' | sort -u \
  | while read p; do [ -f "out$p" ] && echo "ok  $p" || echo "БИТАЯ $p"; done

# Cloudflare отдаёт свежие ассеты, а не старый кэш
curl -s https://24zdorovie.com/og/nutrition-ru.png -o /tmp/live.png
[ "$(md5 -q public/og/nutrition-ru.png)" = "$(md5 -q /tmp/live.png)" ] \
  && echo "✓ свежая версия" || echo "✗ отдаётся старый кэш, нужен purge"
```

Что ещё стоит увидеть в HTML статьи: счётчик Метрики (`ym(111156412`),
`rel="canonical"`, три `alternate` (ru / en / x-default) и разметку
`MedicalWebPage` + `FAQPage`.

## 5. Search Console

Если менялась структура (новые статьи, порог тег-страниц, hreflang) —
пересдать `https://24zdorovie.com/sitemap.xml` в Google Search Console
и Яндекс.Вебмастере. Ключевые новые статьи можно дополнительно отправить
на индексацию вручную.

## Что где настроено

| Что | Где |
| --- | --- |
| Редиректы, HTTPS, www, выбор локали | `public/.htaccess` |
| Заголовки кэша и безопасности | `public/.htaccess` |
| Статический экспорт, trailingSlash | `next.config.ts` |
| OG-картинки по рубрикам | `scripts/gen-og.mjs` |
| Заливка на хостинг | `scripts/deploy.mjs`, доступы в `scripts/.deploy.env` |
| sitemap с hreflang | `src/app/sitemap.ts` |
| Порог индексации тег-страниц | `TAG_INDEX_MIN` в `src/lib/content.ts` |
| Метрика, GA | `SITE.analytics` в `src/config/site.ts` |

## Известные ограничения статики

Серверных маршрутов нет, поэтому:

- форма подписки работает только через внешний сервис —
  полный URL вписывается в `SITE.newsletterEndpoint`, пустая строка прячет форму;
- поиск по сайту — клиентский, по индексу, собранному на этапе сборки;
- любые новые «API-ручки» придётся либо выносить наружу, либо переезжать
  на хостинг с Node.
